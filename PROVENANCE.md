# Provenance

JOCForge-owned Rust code is Apache-2.0. The implementation is based on public
ETSI/ITU/EBU specifications and redistributable open-source references. No
proprietary Dolby encoder binary was used to generate MVP outputs.

## Specifications

- ETSI TS 103 420, public JOC syntax, profiles, OAMD, and EMDF requirements.
- ETSI TS 102 366, public E-AC-3 syncframe, I0/D0, channel-map, and carrier syntax.
- ITU-R BS.2076 / EBU ADM public model semantics.
- ITU-R BS.2088 / EBU BW64 public container semantics.
- ITU-R BS.2127 / EBU ADM Renderer public reference boundary.

`libadm` exposes the public C++ ADM element/reference model for ITU-R BS.2076
ADM XML (including programme/content/object/pack/channel/TrackUID relationships
where represented); upstream documents incomplete sub-element coverage and no
S-ADM. It requires C++11, Boost headers, and CMake. `libbw64` exposes a
header-only C++ BW64/RF64/BWF reader/writer layer for `ds64`, `axml`, `chna`,
and 16/24/32-bit integer PCM; it requires CMake but no runtime library. `libear`
provides independent BS.2127 ADM speaker-render components, requires C++14,
Boost, and recursive submodules, and is not an encoder. The current host exposes
Rust and FFmpeg but no usable `cmake`, `cl`, `g++`, or `clang++` toolchain, so a
C++ FFI bridge would be disproportionate for the overnight MVP. The explicit
decision is `ADM_MVP_INGEST = LIBADM_LIBBW64_NARROW_NATIVE_SUBSET`; migration to
libadm/libbw64 interop is follow-up work. None of these libraries provides JOC
encoding support.

## Other dependencies and roles

- Local development and the current source-checkout validation use FFmpeg 8.1
  as an external executable invoked for deterministic 5-channel E-AC-3 I0
  carrier audio at 1024 kbps and independent decode checks. The observed
  `8.1-full_build-www.gyan.dev` host build reports `--enable-gpl
  --enable-version3`; it is not a JOCForge dependency, is not Apache-licensed,
  and is not redistributed by the source repository. It is not used to claim
  dependent-D0 support; JOCForge writes the PCM-derived D0 syntax itself.
- The intended Windows release bundle uses the separate source-built FFmpeg
  pin in `release/ffmpeg-pin.json`: FFmpeg `n8.1` at commit
  `a65b3bfe9dacc3b20597ef199d0afdd8bc8128e2`, with the official source archive
  hash recorded there. Its frozen configuration enables neither GPL nor
  nonfree code and is audited as LGPL-2.1-or-later. The release workflow keeps
  FFmpeg's license files, source archive, build configuration, local-change
  record, and binary hashes separate from JOCForge's Apache-2.0 license.
- OpenJOC v0.16.0: `VALIDATION_REFERENCE` / external validator / decoder /
  renderer. The exact source revision, Windows x86-64 executable SHA256, and
  commands are pinned in `validation/openjoc-validator.json`; the pin is
  checked before validation. JOCForge production code does not link to OpenJOC
  crates.
- At the 1024 kbps profile/rate cell, JOCForge passes `-channel_coupling 0`
  to the external FFmpeg E-AC-3 I0 encoder. This is a syntax/correctness
  compatibility control: FFmpeg's automatic coupling at 384 kbps produced a
  carrier that pinned OpenJOC could not traverse. It is not perceptual tuning
  and does not alter the declared five-carrier topology or D0 ownership.
- Synthetic fixture: repository-owned deterministic sine-basis PCM, no
  copyrighted music, with a recorded rank-7 ground-truth matrix generated by
  `jocforge fixture`.

## Supplied real file

A separately supplied Logic Pro ADM-BWF export was used for local QA. The file
is not part of this repository, is not required for the controlled public
smoke test, and must be supplied explicitly to scripts that exercise the
source-derived milestone. Its local filename, path, hash, and media contents
are intentionally omitted from public provenance.

The seek-aware scanner handles metadata after a large `data` chunk. The narrow
ADM model accepts the tested 38-track, 48 kHz, 24-bit structure and records the
29 authored objects (28 `Objects` and 1 `DirectSpeakers`) without bundling the
source media.

The generalized clean implementation now ingests the 28 `Objects` plus the
one positioned `DirectSpeakers` component, assigns every supported authored
source to a deterministic reduction cluster, and emits at most 15 coded
representations. The DirectSpeakers treatment is an explicit narrow clean-side
fallback through the positioned source-accounting path; complete non-LFE bed
semantics remain open and are not inferred.

The reduction and carrier paths are implemented by the Clean Implementer from
sanitized behavioral requirements, public specifications, and generic
mathematical methods. No contaminated workspace, private sanitizer material,
or proprietary encoder analysis was used. D0 contains source-window-derived
PCM features for both D0 channels; this remains a source-derived demonstrator,
not a transparent perceptual E-AC-3 encoder.
